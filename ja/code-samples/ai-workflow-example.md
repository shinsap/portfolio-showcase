# 要件定義・実装・レビュー・受け入れの進め方

各案件で使う基本的な進め方です。公開の権限と必要な検証は、案件ごとの合意範囲に従います。同じフォルダのTypeScript・TSXは説明用サンプルで、実案件から抜き出したコードではありません。

herdrを開発作業環境として使い、Claude CodeとCodexを複数のペインで運用しています。案件ごとの作業を整理し、実装とレビューを役割分担して進めています。

1. **課題を定義する。** 利用者、現場の制約、事業目的、提供しない範囲を整理します。
2. **受け入れ条件を決める。** データ・認可の境界、失敗時の挙動、確認可能な合格条件を定めます。
3. **範囲を限定して実装する。** Claude Codeなどがコード、必要なテスト、文書を更新します。
4. **独立してレビューする。** Codexなどが要件と差分を照合。自分は根拠・影響・操作性・運用コストを踏まえ、修正・受容・保留を判断します。
5. **対象に合った検証を行う。** 単体テスト、配布CLI、配信済みプレビュー、実機確認は異なる問題を確認します。合格した範囲と未確認の範囲を残します。
6. **公開と運用へつなぐ。** 案件ごとの権限に従ってコミット・配信し、挙動が変わる際は運用手順も更新します。PRマージだけで配信済みとは判断しません。

## 判断によって開発を変更した例

- [BQmenu](../projects/bq-menu.md)：PDF配信を要件に整合させ、部分的な削除失敗を診断して再試行まで確認。
- [切り身重量合わせ](../projects/portion-weight-match.md)：反例からアルゴリズムを変更。静的レビューの診断もブラウザ実測で訂正。
- [RepoBD](../projects/repobd.md)：配布パッケージを検証し、ローカル書き込み後にサーバー処理が不確定になるケースを設計。
- [Vulneramigo](../projects/vulneramigo.md)：配信済みプレビューで更新失敗・オフライン利用・復旧を確認。
- [Hit & Lock](../projects/hit-and-lock.md)：事前条件を定めた範囲で自動マージと本番確認を行う別枠の実験。

AIを実装・レビューに活用し、自分は課題、提供範囲、受け入れ条件と、修正・公開・停止の判断を担当します。
