# RepoBD


## 失敗時の処理と公開前検証

ローカルのファイル書き込みと、サーバーの使用済み処理は一つのトランザクションにはできません。そのため、配送の期限付き確保、復号・検証、必要に応じた上書き確認、確保状態の再確認、書き込みと読み戻し、使用済み処理の順に扱います。書き込み確認後の通信が失敗した場合は、ファイルを再度書き換えず、回数を限定して再試行します。同じ値が既にあれば再書き込みなしで完了できます。

これは設計・テストした失敗モードであり、本番事故の復旧実績や、複数システムをまたぐ厳密な一回実行の保証ではありません。v0.1.1の引き継ぎ記録では19ファイル・968テスト、ビルド・型検査が通過しています。ソースを直接動かすだけでなく、npm配布物をインストールし、本番APIに合成データで正常系・repo不一致・再利用・期限切れなどのE2E確認を行いました。

## 概要・企画の起点

複数のターミナルで作業中、正しいAPIキーを誤ったリポジトリへ設定した経験から開発したCLIです。暗号化したキーの一回限りの受け渡しと、取得前のGit origin照合を組み合わせます。個人開発、AIエージェントを使う複数repoの作業、開発者間の引き継ぎが用途です。

## 要件と技術設計

- 送信側でAES-256-GCMにより暗号化。配送ごとに新しいキーを使用。
- 受信側ではcanonical Git originを先に確認。不一致なら配送処理のネットワーク通信前に停止し、取得・書き込み・消費を行わない。
- 有効期限は15分。使用済み・期限切れの配送は拒否。
- Cloudflare WorkersとD1が短期間の暗号化データと配送状態を管理。対応CLIのフローでは平文・復号キー・リポジトリ識別情報をバックエンドへ送らない。
- リポジトリ直下の`.env`へ限定した書き込みを行い、曖昧・非対応の内容は推測で変更しない。

## 保護範囲の判断

Gitの照合は操作ミスを減らす仕組みであり、受取人の認証ではありません。同一repo内のブランチ・本番／検証環境・キーの用途・利用者の違いは識別しません。秘密情報の保管庫、IAM、悪意あるローカル利用者や侵害済み端末への防御としては設計していません。

配送URL自体も秘密情報として扱い、信頼できる私的な経路で渡す必要があります。こうした境界を実装前の要件として明示し、用途を広げすぎない判断をしました。

## 担当と開発体制

自分が課題・要件・脅威モデル・受け入れ条件・公開範囲を定義し、修正とリリースを判断しました。Claude Codeが実装、Codexが独立した差分・セキュリティレビューを担当しています。CLIだけでなく、バックエンド、npm配布、OSS文書、LPまで整備しました。
